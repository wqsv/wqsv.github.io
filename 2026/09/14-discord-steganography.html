Building Robust Image Steganography That Survives Discord

by wqsv · 10–13 minute read

⌂Home ↗GitHub

September 14, 2026 — 10–13 minute read

Steganography is often introduced with a simple example: take an image, replace the least significant bits of some pixels with a message, and recover the message later.

That works when the encoded image is preserved exactly. It becomes a very different problem when the image passes through a platform such as Discord, which may resize or re-encode the image before the receiver gets it. The hidden data must therefore survive a lossy channel.

To make the problem concrete, the initial goal was to hide a short sentence in a profile picture and recover it after Discord processed the image. The exact details of Discord's image-processing pipeline are not treated as a public specification here; the behavior described below is based on the observed test path.

This write-up documents the path from a basic LSB implementation to a working keyless DCT-domain steganography system that successfully recovered a short message after Discord profile-picture processing.

The final system is not a standard named algorithm. It is a combination of established techniques:

  • 8x8 DCT
  • coefficient-difference embedding
  • BCH(31,21) error correction
  • deterministic interleaving
  • repetition coding
  • CRC32 integrity checking

The individual techniques are standard. The exact combination and parameters were chosen experimentally for this particular carrier and transformation.

Note on scope and platform behavior

This experiment is specifically about Discord profile pictures, not images uploaded as ordinary attachments.

The carrier used in the experiment is a 1024x1024 PNG. The PNG is first modified by the steganographic encoder. The resulting encoded PNG is then used as a Discord profile picture. The tested retrieval path returned the profile picture as WebP, so the decoder does not receive the original encoded PNG.

The actual channel being tested is therefore:

1024x1024 source PNG

steganographic encoder

1024x1024 encoded PNG

This distinction is important. The goal is not to design a general-purpose steganography system for arbitrary Discord images or attachments. The parameters in this write-up were selected around this specific 1024x1024 profile-picture → WebP pipeline.

Consequently, values such as the DCT coefficient locations, embedding strength, repetition factors, and resulting payload capacity should be understood as experimentally chosen parameters for this channel, rather than universal steganography constants.

1. The problem

1.1 The carrier and the channel

The carrier image was a 1024x1024 black-and-white VHS-style image.

The goal was to hide a short plaintext message and recover it after the image was used as a Discord profile picture.

The decoder receives the processed image rather than the original encoded PNG:

Encoded PNG
Discord profile-picture processing
Downloaded WebP

The task is therefore to encode information in a form that remains recoverable after this transformation.

1.2 The embedding budget

With an 8x8 DCT grid, a 1024x1024 image contains 1024/8=128 blocks along each dimension and therefore 128x128=16,384 blocks in total.

That number looks large until redundancy is introduced. A block is only a carrier location; it is not necessarily one useful message bit. Repetition, error-correcting codes, interleaving, and other robustness mechanisms consume many of those locations.

Parameter Value Why it matters
Carrier 1024×1024 Fixed size used for this experiment
DCT block 8×8 Gives a regular block grid for the transform
Blocks 16,384 One coefficient-pair measurement can be taken per block
Coefficient pair (2,3)/(3,2) Empirical robustness/distortion compromise
Δ 20 Separates the two coefficient-difference states
Header repetition 25× Adds redundancy to critical metadata
Payload repetition 30× Adds more redundancy to the larger payload
ECC BCH(31,21), t=2 Corrects up to two bit errors per codeword
Shuffle seed 0x6D2B79F5 Fixed public seed for reproducible block ordering

The design problem is to choose a representation, redundancy budget, and reconstruction strategy that remain usable after the channel changes the carrier.

2. LSB as the baseline

2.1 Baseline rationale

LSB steganography is the obvious baseline because it is simple and has excellent raw capacity. For an 8-bit channel value such as:

10110110

the least significant bit is the final bit. Changing it from 0 to 1 changes the value by only one:

182 = 10110110
183 = 10110111

For an unchanged image, this is attractive: the modification is tiny and straightforward to decode.

2.2 Baseline failure

The problem appeared as soon as the carrier passed through Discord and it was obvious.

LSB encoding depends on exact pixel values. If a transformation changes a value from:

10110110

to:

10110111

the visual change may be negligible, but the hidden bit has changed.

That is exactly what happened in the experiment. The images could remain visually similar while enough pixel values changed to destroy a large fraction of the embedded bits. The decoder eventually interpreted arbitrary image data as a message length such as:

2456687191

The problem was the representation being used to carry the information.

2.3 First paradigm shift

The first implementation treated individual pixels as storage locations. The failure showed that exact pixel values were too fragile for the channel being tested.

The design question therefore changed from "Which pixels should contain the message?" to "Which representation of the image gives us a more useful signal to modify?"

That led to the transform domain.

2.4 Experimental progression

The final system is easier to understand if the intermediate failures are made explicit. The design was not obtained by selecting DCT, BCH, and interleaving in advance. Each layer was added in response to a failure mode observed in an earlier experiment.

Attempt Main idea Observed problem Design consequence
RGB LSB Store message bits directly in pixel least-significant bits Discord processing changed exact pixel values and destroyed the hidden bitstream Move away from exact pixel values
DCT coefficient embedding Store information in transform coefficients Some coefficient choices were not sufficiently stable after processing Treat coefficient selection as an empirical problem
Stronger DCT embedding Increase the separation of the embedded states Residual bit errors remained despite stronger embedding Add explicit redundancy and error correction
75x repetition Repeat coded bits many times A 216-bit coded payload consumed 16,200 of 16,384 blocks, leaving almost no spatial budget Use repetition selectively rather than as the sole protection mechanism
Hamming(15,11) Correct one error per codeword Some codewords could accumulate multiple errors Use an ECC with a larger correction capability
BCH(31,21) Correct up to two errors per codeword Payload recovery improved, but weak metadata could still invalidate the result Protect the header as well as the payload

Final combination DCT difference + repetition + interleaving + BCH + CRC32 Successful tested Discord profile-picture round-trip Retain the layered architecture

This progression is important because the individual techniques do not solve the same problem. DCT changes the representation in which information is embedded. The coefficient margin makes that representation less sensitive to small numerical changes. Repetition supplies multiple observations. Block shuffling distributes those observations spatially. Interleaving changes the shape of burst errors presented to the ECC. BCH corrects residual errors, and CRC32 determines whether the final reconstruction should be accepted.

The resulting system is therefore better understood as a small communication chain than as a single steganographic trick. The engineering objective is to make the entire chain tolerate the particular transformation introduced by the tested platform.

3. Moving into the DCT domain

3.1 8x8 DCT blocks

Instead of working directly with pixel values, each 8x8 image block is transformed into 64 frequency coefficients using the Discrete Cosine Transform (DCT).

Conceptually:

8×8 pixel block
DCT
64 frequency coefficients

The coefficients describe different spatial frequencies. Values near the top-left represent broad, low-frequency structure; moving away from that region represents progressively finer detail.

The transform domain is useful because image processing does not affect all components equally. Higher-frequency information is often more vulnerable to compression, while modifying very low frequencies can create visible changes.

The useful region is therefore a compromise: coefficients that are stable enough to survive the tested processing, but not so visually important that changing them becomes obvious.

3.2 Coefficient-pair selection

The experiment tested different DCT coefficient relationships rather than assuming that one frequency location would always be optimal.

The final implementation uses:

(2,3) <-> (3,2)

This pair provided a practical balance between robustness and visible distortion for the tested Discord profile-picture pipeline.

It should not be treated as a universal DCT location. A different image or processing pipeline could produce a different optimum.

3.3 Relationship-based embedding

Let the selected coefficients be A and B.

The decoder does not depend on their exact original values. It only checks their ordering:

A - B >= 0 → 1A - B < 0 → 0

This is more useful than embedding a bit directly into the value of a coefficient because a small change to both coefficients does not necessarily change their ordering.

3.4 Embedding margin

Simply choosing which coefficient is larger is still fragile if the difference is small. The encoder therefore creates a deliberate margin between them.

First compute their midpoint:

midpoint = (A + B) / 2

Then choose a target difference:

0 → target difference = -Δ1 → target difference = +Δ

and reconstruct the pair around the same midpoint:

A = midpoint + target / 2
B = midpoint - target / 2

The final implementation uses:

Δ = 20

so the intended difference is approximately -20 for a 0 and +20 for a 1.

The important quantity is the relationship between the coefficients and the margin separating the two states, not the absolute coefficient values.

This is a coefficient-difference embedding scheme. It has similarities to Quantization Index Modulation (QIM), although describing it as QIM-like is more accurate than claiming it is a textbook QIM implementation.

3.5 Luminance-channel embedding

The embedding is applied to the image's luminance channel rather than independently to all RGB channels.

RGB
YCbCr
Ymodified
Cbunchanged
Crunchanged

Only Y is divided into 8x8 blocks and modified. The channels are then recombined and converted back to RGB.

This keeps the chrominance channels untouched and places the hidden signal in image luminance.

The second paradigm shift is therefore simple:

Encode information in a relative property of a transform representation, rather than in exact pixel values.

That makes the payload less dependent on the exact numerical state of the carrier, but it does not make every decoded bit correct. The next problem was what to do about the errors that still remained.

4. Adding redundancy

4.1 Repetition

Even with a better carrier representation, some individual measurements can still be wrong after processing.

A simple response is to embed the same bit multiple times.

For example, with 25 copies:

original bit = 1

19 observations → 1
 6 observations → 0

A majority vote still recovers the original bit.

Repetition does not improve any individual observation. It simply gives the decoder multiple observations of the same information.

The final configuration uses:

Header:  25×
Payload: 30×

These are empirical parameters for the tested carrier, not universal constants.

4.2 Capacity cost

Repetition consumes blocks very quickly.

The carrier contains 16,384 blocks. One experiment used a repetition factor of 75 for a test payload requiring 216 coded bits: 216x75=16,200 blocks.

That leaves almost no room for anything else. More importantly, errors could still remain.

This exposed a hard limit: repetition can provide many observations, but it does not provide structured knowledge about the data and it does not scale efficiently with the amount of redundancy required.

4.3 Hamming(15,11)

The first error-correcting code tested was Hamming(15,11). It takes 11 data bits and adds 4 parity bits to form a 15-bit codeword.

The parity bits occupy positions that are powers of two:

P1  P2  P4  P8

The remaining positions contain the data bits. Each position has a binary representation, and that representation determines which parity checks include the position.

For example:

11 = 1011₂

so position 11 participates in the P8, P2, and P1 checks.

If bit 11 is corrupted, those three parity checks fail. The failed-check pattern forms the syndrome:

P8  P4  P2  P1
 1   0   1   1

which is:

1011₂ = 11

The decoder can therefore identify and correct the corrupted bit.

Hamming(15,11) is designed to correct one bit error per codeword. With multiple errors in the same codeword, the syndrome is no longer guaranteed to identify a single valid error location.

So Hamming demonstrated an important advantage over repetition: its redundancy is structured around the relationships between bits, allowing the decoder to correct errors instead of merely choosing the majority value.

The experimental pipeline was:

Message bits
Hamming encoding
Repetition
DCT embedding

and in reverse:

DCT extraction
Repetition voting
Hamming decoding
Message bits

The experiment showed that this was still not enough for the observed channel errors.

4.4 CRC32 integrity checking

A correct-looking decode is not necessarily a correct decode. The message therefore carries a CRC32 value calculated from the original payload:

CRC32(message)

After reconstruction, the decoder calculates the CRC again. If the values differ, the reconstruction is rejected.

CRC32 is an error detector, not an error-correcting code. Its job is to tell us whether the output of the recovery process should be accepted.

That made the development process much more reliable. Instead of treating arbitrary decoded bytes as a successful message, the decoder had an explicit integrity test.

4.5 Second paradigm shift

The experiments changed the design objective again.

The problem was no longer "How do we prevent every bit from changing?" It became "How do we reconstruct the original information even when some bits are wrong?"

That is a communication-system problem rather than a pure pixel-hiding problem.

But there was another complication: the errors were not necessarily independent.

5. Matching protection to the error pattern

5.1 Correlated errors

Suppose 25 copies of a bit are placed in nearby blocks:

block 1  → 1
block 2  → 1
block 3  → 1
...
block 25 → 1

A local image artifact can affect many of those blocks at once.

Instead of 25 independent opportunities to recover the bit, the decoder may see a cluster of damaged observations:

25 copies
Local artifact
Many copies damaged together

These are correlated errors. Repetition works best when the errors are spread out; it performs poorly when a local disturbance destroys many copies together.

5.2 Spatial distribution of repeated observations

The solution is to distribute related observations throughout the carrier instead of placing them in contiguous blocks.

Conceptually:

bit A → blocks 17, 438, 2911, 9042, 15003, ...

rather than:

bit A → blocks 1, 2, 3, 4, 5, ...

The final implementation uses a deterministic permutation of the available blocks with the public seed:

0x6D2B79F5

The seed is not a secret. It exists so that encoder and decoder generate the same ordering.

The purpose is purely spatial: a local artifact is less likely to destroy all repeated observations of the same bit when those observations are distributed across the image.

5.3 Interleaving

There is a related problem inside the error-correcting code.

Suppose a local artifact destroys four nearby embedded bits. Without interleaving, those bits might belong to the same BCH codeword:

One codeword
4 corrupted bits

That is difficult for a code designed to correct only a small number of errors per codeword.

Interleaving changes the placement of coded bits so that nearby carrier positions correspond to different codewords.

For example:

coded stream:
A B C D E F G H

interleaved:
D A H C F B G E

The decoder applies the inverse permutation after extraction.

Now a local burst is more likely to become something like:

codeword X → 1 error
codeword Y → 1 error
codeword Z → 1 error
codeword W → 1 error

instead of four errors concentrated in one codeword.

The system therefore has two distinct kinds of distribution:

  • Block shuffling spreads repeated observations across the image.
  • Interleaving spreads coded bits across different ECC codewords.

Both are deterministic and reversible.

5.4 BCH(31,21)

The Hamming experiment showed that the error-correcting code needed to tolerate more than one error per codeword.

The next step was BCH(31,21).

It takes 21 information bits and produces a 31-bit codeword:

21 information bits
        |
        v
   BCH encoder
        |
        v
31 coded bits

The implementation uses:

t = 2

so the code is configured to correct up to two bit errors per codeword.

That gives more error tolerance than Hamming(15,11):

Hamming(15,11)Correct 1 error
BCH(31,21)Correct up to 2 errors

The additional redundancy costs capacity, but the payload is intentionally small and survival of the tested processing is more important than maximizing raw capacity.

The complete protection stack is now:

DCT coefficient difference
          ↓
      repetition
          ↓
     interleaving
          ↓
      BCH ECC
          ↓
        CRC32

The important design lesson is that the layers do different jobs. Repetition provides multiple observations; interleaving changes the shape of burst errors; BCH corrects residual errors inside codewords; CRC32 decides whether the final reconstruction is acceptable.

6. Protecting the whole message

6.1 Protecting metadata

The first BCH version substantially improved payload recovery, but the CRC still failed.

The remaining weak point was the header.

The header contains the information needed to interpret the payload:

magic
message length
CRC

If the metadata is corrupted, the decoder can reject an otherwise recoverable payload.

The header therefore cannot be treated as a separate, less important piece of data. It is part of the protected message.

6.2 BCH protection for the header

The fix was straightforward: protect the header with the same BCH-based pipeline used for the payload.

The current header format is:

4-byte magic
2-byte message length
4-byte CRC32

or:

>BCH7
uint16 length
uint32 CRC

Both header and payload are now BCH-protected and passed through the same interleaving/repetition machinery.

This removed a failure mode in which the payload was recoverable but the metadata prevented the decoder from interpreting it correctly.

6.3 Division of responsibility

The resulting division of responsibility is:

RepetitionMultiple observations
InterleavingReduce burst concentration
BCHCorrect residual errors
CRC32Accept or reject the reconstruction

The CRC is deliberately last. The decoder does not pretend that a structurally valid sequence of bytes is necessarily the original message.

7. Simplifying the carrier modification

7.1 Multiple-pair embedding

An earlier implementation embedded the same bit into two coefficient pairs per block:

(0,1) ↔ (1,0)(1,2) ↔ (2,1)

That provided another local vote, but it also meant that every embedded bit modified four DCT coefficients.

The experiment showed that this additional local redundancy was not necessary once the system already had repetition, interleaving, BCH, and spatial distribution.

7.2 Final coefficient pair

The final implementation uses a single pair:

(2,3) ↔ (3,2)

The decoder therefore makes one coefficient-pair measurement per block.

This is the same pair described earlier as the best practical compromise found for the tested carrier and processing pipeline.

7.3 Distortion versus redundancy

The tradeoff was:

More coefficient pairs
More local redundancy
More coefficient modifications
More visible distortion

versus:

Fewer coefficient pairs
Less local redundancy
Less visible modification
Reliance on system-level redundancy

The final design deliberately chooses the second path.

This is a useful engineering result: redundancy is not automatically beneficial simply because it improves recoverability. It also has a visual cost and a capacity cost.

9.2 Practical capacity

The raw carrier contains 16,384 8x8 blocks, but those blocks are heavily consumed by redundancy.

The header is 10 bytes:

10 × 8=80

bits.

BCH(31,21) expands this to four 31-bit codewords:

4 × 31=124

coded bits.

At 25x repetition:

124 × 25=3,100

blocks are used for the header.

That leaves:

16,384-3,100=13,284

blocks for the payload.

With 30x payload repetition, the available coded payload is approximately:

13,284/30\approx442

coded bits.

Fourteen BCH codewords require:

14 × 31=434

coded bits and carry:

14 × 21=294

data bits.

That is enough for:

36 bytes = 288 bits

with some room remaining.

The practical capacity of the current robust configuration is therefore:

36 bytes per 1024x1024 image

This is not an information-theoretic limit of the image. It is the capacity of this particular parameter set.

9.3 Robustness versus capacity

Most of the carrier is deliberately spent on redundancy:

BCH overhead
+
25x header repetition
+
30x payload repetition
+
interleaving
+

Reducing that redundancy would increase capacity, but it would also reduce the margin against the same processing pipeline.

The earlier 75x repetition experiment illustrates the tradeoff clearly. A 216-bit coded payload would require:

216 × 75=16,200

blocks out of 16,384 available blocks.

That leaves almost no room for anything else, and errors could still remain.

The design therefore favors robustness over raw capacity because the payload is intentionally small.

9.4 Standard techniques versus project-specific choices

There is no single standard algorithm called "DCT-BCH steganography" that exactly matches this implementation.

9.5 Limitations and interpretation

The successful round-trip demonstrates that the final configuration survived the specific Discord profile-picture processing path that was tested. It does not establish that the same parameters will survive every Discord image operation, every image format, every resize, or every compression setting.

Several limitations therefore matter when interpreting the result:

  1. The channel is specific. The system was tuned around a 1024x1024

profile-picture → WebP pipeline. A different platform or processing path may require different coefficient locations, embedding strength, repetition factors, or error-correction parameters.

  1. The coefficient pair is empirical. (2,3)/(3,2) is the pair selected

for this experiment. It should not be presented as a universally optimal DCT location.

  1. The embedding margin is empirical. Δ = 20 is a parameter of the

tested implementation. Increasing it may improve tolerance to some perturbations while increasing distortion; decreasing it may preserve more of the carrier while reducing the separation between the two decoded states.

  1. Capacity is intentionally small. The reported 36-byte payload is the

practical capacity of this parameterization after BCH overhead and repetition. It is not an information-theoretic limit of the image or of DCT-domain steganography.

  1. The system is not cryptographic. There is no secret key or encryption.

The public shuffle exists for deterministic spatial distribution, not for secrecy. Anyone who knows the scheme and parameters can in principle decode the payload.

  1. The result is an empirical demonstration, not a universal robustness guarantee.
A successful round-trip is strong evidence for the tested channel, but broader claims would require a larger experiment across multiple images, transformations, and processing conditions.

These limitations are not weaknesses in the engineering argument. They define what the experiment actually demonstrates and prevent a channel-specific parameter set from being mistaken for a universal recipe.

The important conceptual change was that the hidden message no longer had to survive perfectly. It became a redundant signal from which the original information could be reconstructed.

The system was therefore designed to survive errors, not to pretend that errors would never occur.

10.2 Security versus robustness

The final system is not cryptographic.

There is:

  • no password,
  • no secret key,
  • no encryption.

Anyone who knows the image format, DCT scheme, coefficient location, repetition counts, BCH parameters, interleaving permutation, and public block permutation can decode the message.

That was intentional. The requirement was to hide the existence of the message, not to cryptographically protect its contents.

Steganography
    ≠
Encryption

Steganography asks whether information can be hidden inside another carrier. Encryption asks whether someone who sees the data can understand it.

The useful engineering takeaway is:

**Steganography for a lossy platform is not primarily about hiding

bits. It is about designing a representation, redundancy scheme, and

decoder that survive the channel.**
